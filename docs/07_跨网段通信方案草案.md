## 2. 现状确认：为什么现在跨不了网段

**结论：当前版本只支持同一子网内通信，跨网段必然失败。** 证据链：

1. **环境无网关**：`03` §7 启动命令 `sudo mn --topo=tree,2,2 --mac`（Mininet 默认
   `10.0.0.0/8` 单平坦子网，主机无 `defaultRoute`）；拓扑里只有 OVS + ONOS，**没有三层节点**。
2. **流表只做二层语义转发**：`02` §3.6 的 IPv4 规则匹配 `IN_PORT + ETH_TYPE + 源/目的 /32`
   → 动作仅 `OUTPUT`。**不改 MAC、不减 TTL**——跨网段必需的「网关改写 MAC / TTL 递减」无人承担。
3. **ARP 语义是同子网的**：跨网段时源主机 ARP 的是**网关 IP** 而非目的主机 IP；
   FR-07b（乙-2b，未实现）规划的 ARP 放行规则是同子网语义，罩不住网关场景。
4. **host_table / deployed 按 IP 直连假设建模**：`02` §4.2 每个 IP 一个位置；
   `02` §4.4 `deployed` 一条路径。跨网段的通信对在数据面上是**两段路径**（源→网关、网关→目的），
   现有 `deployed` 结构表达不了。

## 3. 目标场景与拓扑

### 3.1 演示拓扑（在带环拓扑基础上加网关，兼顾 A4 断链自愈）

```
        子网 A: 10.0.1.0/24                子网 B: 10.0.2.0/24

  h1(10.0.1.2)──┐                 ┌──h3(10.0.2.2)
                S1──────────S2───S3
  h2(10.0.1.3)──┘    │  (环)   │  └──h4(10.0.2.3)
                     └──r0─────┘
                  gw:10.0.1.1(端口a) gw:10.0.2.1(端口b)
                  Linux 主机，sysctl ip_forward=1
```

> r0 的接入位置（挂 S1+S3，还是挂 S2 双臂）❓ 待甲实测定；上图「双臂挂 S1/S3」仅为示意。
> 链路冗余（环）保留：跨网段两段各自也要满足 A4 的断链自愈要求。

### 3.2 IP 规划（✅ 定稿候选）

| 节点 | IP | 角色 |
|---|---|---|
| h1 / h2 | `10.0.1.2` / `10.0.1.3`，gw=`10.0.1.1` | 子网 A 主机 |
| h3 / h4 | `10.0.2.2` / `10.0.2.3`，gw=`10.0.2.1` | 子网 B 主机 |
| r0 | `10.0.1.1`（接口 a）/ `10.0.2.1`（接口 b） | Linux 软件网关（`ip_forward=1`） |

Mininet 自定义拓扑脚本（甲维护，`ipBase` + `defaultRoute` 或手工 `ip addr add`）❓ 细节甲定。

### 3.3 数据面行为（方案 A 下一次跨网段 ping 的完整路径）

```
h1: ping 10.0.2.2 (dst MAC = 10.0.1.1 的 MAC)
  ↓ ① ARP: h1 广播 "who has 10.0.1.1" → r0 内核直接应答（真实网关，天然支持）
  ↓ ② 段1流表（源子网侧）: 匹配 (IN_PORT=h1端口, IPv4, src=10.0.1.2/32, dst=10.0.2.2/32)
      沿 S1→…→r0 接入交换机逐跳 OUTPUT —— 复用现有 dijkstra + path_to_flows
  ↓ ③ r0 内核路由: MAC 重写(dst MAC=10.0.2.2), TTL-1 —— 由网关内核完成，大脑不管
  ↓ ④ 段2流表（目的子网侧）: 匹配 (…, src=10.0.1.2/32, dst=10.0.2.2/32)
      沿 r0 另一接口接入交换机→…→S3 逐跳 OUTPUT
  ↓ ⑤ 回程: h3 → 10.0.2.1(网关) → r0 路由 → h1，反向流表同理（FR-07b 双向规则的跨网段版）
```

**关键观察**：两段的流表匹配条件完全相同（都按**端到端** `dst IP /32` 匹配），
现有 `path_to_flows` 的匹配语义**一行都不用改**，改的只是「一次通信对要装两段路径」。

## 4. 技术方案比选（周四碰头定 A/B）

| 方案 | 做法 | 优点 | 缺点 / 风险 | 建议 |
|---|---|---|---|---|
| **A · Linux 软件网关**（如上） | Mininet 加一台主机做路由器，`ip_forward=1`；大脑按「两段路径」下发流表 | `path_to_flows` 匹配语义零改动；MAC 重写/TTL 由内核做，**不需要验证 ONOS 改写指令**；网关 ARP 内核天然应答；回退容易 | 网关是「控制器外的转发节点」，答辩要讲清「SDN 控制的是两段二层织物，网关是传统 L3 边界」——这本身是真实网络的常见形态 | **✅ 推荐（第一阶段）** |
| B · 分布式 L3 网关（流表改写 MAC） | 接入交换机当网关：流表 `mod_dl_src/mod_dl_dst` + TTL 递减，控制器回答网关 ARP | 全程 SDN 化，演示更「炫」 | `path_to_flows` 大改（首跳按前缀、后续按 MAC 匹配，两套语义）；ONOS REST 对 `DEC_TTL`/改写指令的支持 ❓ 全未实测；网关 ARP 要 packet-out 或 proxyarp 配置，❓ | 第二阶段可选加分，先留口子 |
| C · ONOS vRouter / SR | 用 ONOS 自带三层应用 | 官方组件 | 违反「不写/不依赖 ONOS 内部应用」既定路线（`01` §4），复杂度失控 | 否决 |

## 5. 控制面（乙）设计要点——评审重点

### 5.1 网关解析：新增纯函数（建议落 `flow.py` 或 `path.py`，乙的文件）

```python
def resolve_legs(key: tuple[str, str], host_table: dict,
                 gateways: dict[str, str]) -> list[tuple[str, dict]] | None
    # key=(源IP,目的IP)。同子网 → 返回 [单段]（现状行为，完全向后兼容）；
    # 跨子网 → 返回两段 [(源IP, 网关IP_src侧), (网关IP_dst侧, 目的IP)]，
    #           每段给出该侧端点的 host 记录（网关的两个接口是 host_table 里两条独立记录）；
    # 任一端点不在 host_table / 子网无网关配置 → 返回 None（调用方按 unknown_host/unknown_gateway 报错）
```

- `gateways` 映射「子网前缀 → 该子网侧网关 IP」进 `config.py`（甲维护常量，只 import 不改）：
  `{"10.0.1.0/24": "10.0.1.1", "10.0.2.0/24": "10.0.2.1"}`
- 网关在 ONOS 里是**两个普通 host**（两网卡两 MAC 两 IP，两处 location）——
  `build_host_table` **结构零改动**，天然得到 `10.0.1.1` 与 `10.0.2.1` 两条记录。❓ 待实测确认
  （ONOS 对转发节点双接口的 host 学习可能有意外，见 §8 风险 1）。

### 5.2 `install_path` / `deployed` 的扩展（**只加不改**，符合 `02` §0）

- `deployed` record **新增可选字段 `legs`**：

```python
{ ("10.0.1.2","10.0.2.2"): {
      "path":     [...],        # 段1路径（保留原字段，取第一段，兼容旧读方）
      "out_ports":[...],        # 同上
      "flow_ids": [...],        # 全部流（两段合并，uninstall 按它精确删，语义不变）
      "legs": [ {"path": [...], "out_ports": [...]},   # 段1：源→网关A侧
                {"path": [...], "out_ports": [...]} ], # 段2：网关B侧→目的
      "installed_at": ...,
      # status/priority/rules/unknown_flows/retired_flow_ids 等既有扩展字段含义不变，覆盖两段合计
  } }
```

- `install_path` 内部改为：`resolve_legs` → 逐段 `dijkstra` → 逐段构流 → **两段全部下发成功才算 ok**；
  失败回滚范围 = 两段已下的全部 flowId（沿用现有回滚与 unknown 语义）。
- `uninstall` / `affected` / `recompute` **签名零改动**：它们只消费 `flow_ids` 与重算
  （recompute 内部重新 `resolve_legs` 即可，key 仍是 `(源IP,目的IP)`）。
- 丙的调用点**零改动**（参数与返回值形状不变）；`/api/route` 入参不变，
  新增一种错误码 `unknown_gateway`（源/目的子网无网关配置，HTTP 200 `ok:false`，走 §7 不可达口径）。

### 5.3 ARP 规则（与乙-2b 合并设计，一次解决同子网 + 跨网段）

| ARP 场景 | 谁应答 | 转发规则 |
|---|---|---|
| 同子网 h1↔h2 | 对端主机 | FR-07b 既定方案（放行/逐端口输出）❓ 待真机定 |
| 跨网段 h1→网关 `10.0.1.1` | **r0 内核**（真实网关，天然应答） | ARP 广播需能沿段1路径到达 r0 接入端口——**不能用盲目泛洪**（带环拓扑会成环）❓ |
| 跨网段网关→h3 | h3 | 同上，段2路径 |

**带环拓扑 + ARP 广播 = 广播风暴风险**，这是本方案最大的技术未知数 ❓。候选解法（联调时按序试）：
1. ONOS `proxyarp` app 若默认开启，其 packet-in/回答可能直接接管 ARP（`fwd` 必须关，`proxyarp` 是否保留待实测 ❓）；
2. 大脑对每个已部署通信对下发**定向 ARP 规则**（按 ARP 目标 IP + 入端口精确匹配，沿路径逐跳输出）；
3. 拓扑内环上跑生成树（STL/ONOS 内置）——不倾向，脱离本课题范围。

### 5.4 对既有逻辑的兼容性核对

| 模块/约定 | 影响 |
|---|---|
| `dijkstra` | **零改动**（段1/段2 都是普通交换机图最短路） |

| `install_path/uninstall/affected/recompute` | 签名零改动；内部多段化 |
| `02` §3.6 注 4「相同规则复用」 | 跨网段重算时两段独立判定复用，语义不变 |
| FR-11 多对隔离 | 按 key 隔离，天然兼容 |
| 丙 `main.py` | **零改动**（除 `unknown_gateway` 错误码文档化） |

### 7.1 `04` §7 新增 FR（提交 PR 时写入）

### 7.2 `04` §4 新增 A7 验证命令（骨架，生效后补全）

```bash
# 1) 自定义拓扑 + 网关（甲-9 产物）
sudo mn --custom topo_gw.py --topo mytopo --controller=remote,ip=127.0.0.1,port=6653 --mac --switch=ovs,protocols=OpenFlow13
# 2) 跨网段下发
curl -s -X POST localhost:8000/api/route -H 'Content-Type: application/json' \
  -d '{"src":"10.0.1.2","dst":"10.0.2.2"}'
# 3) 判据
h1 ping -c 3 10.0.2.2            # 0% loss
sudo ovs-ofctl -O OpenFlow13 dump-flows s1   # 段1规则（dst=10.0.2.2）
sudo ovs-ofctl -O OpenFlow13 dump-flows s3   # 段2规则（dst=10.0.2.2）
# 4) 断链自愈（跨网段版 A4）：断段1/段2各一条链路，10s 内 ping 恢复
```

### 7.3 N6 边界项扩展（乙-7 填 `06` 时一并测）

- 跨网段对断链后自愈 <10s（段1、段2 各测一次）
- 网关网口 down（r0 单接口故障）→ 算路返回 `unreachable` 而不崩 ❓（ONOS 对 r0 接口消失的 host 表现待实测）
- 同子网对与跨网段对**并存互不干扰**（FR-11 的跨网段版）
