## 1. 选型原则（顺序不可调换）

1. **出处优先**：能在七份实验指导里找到原文的，优先。被人问「为什么用这个」，答案应该是「实验 X 第 Y 节」，而不是「大家都这么用」。
2. **可解释优先于先进**：一个能讲清原理的 `dict` + 手写 Dijkstra，胜过一行 `nx.shortest_path()`。
3. **依赖最少**：每多一个第三方包，就多一个装不上的风险（本机已踩过 Docker 拉镜像的坑，对网络依赖高度警惕）。
4. **性能最后**：拓扑规模是个位数交换机、个位数主机，O((V+E)logV) 和 O(V²) 的差别在这个规模下没有意义。

## 2. 逐项论证

### 2.1 HTTP 客户端：`requests` + `aiohttp` 双轨（不是二选一）

**结论**：两个都装，分工使用。`aiohttp` 是主链路，`requests` 是诊断脚本。

**为什么不能只用一个：**

- 只用 `requests`：Sanic 跑在 asyncio 事件循环里。`requests.get()` 是同步阻塞调用，
  一个 3 秒超时的 REST 请求会把整个事件循环卡住 3 秒——期间所有 WebSocket 推送、所有 HTTP 请求全部停摆。
  轮询间隔 5 秒、每次卡 1–3 秒，前端图表会一顿一顿地跳。**这是本项目最容易踩的性能坑。**
- 只用 `aiohttp`：写一次性诊断脚本时要手动 `async def` + `asyncio.run()`，啰嗦；
  而且实验⑦全篇用 `requests` 示范，被问「你按实验书做了吗」时需要有对应代码。

**分工定义（写进 02 契约）：**

| 文件 | 库 | 用途 |
|---|---|---|
| `onos.py` | `requests` | 同步接口。诊断脚本、单元测试、现场演示单条命令 |
| `onos_async.py` | `aiohttp` | 异步接口。轮询主循环、`asyncio.gather` 并发拉三个端点 |

两个文件暴露**同名函数**，签名一致，只是 async 与否。这样上层换实现只改 import。

**淘汰的替代品：**

| 候选 | 淘汰理由 |
|---|---|
| `httpx` | 功能上更好（同时支持同步/异步），但**实验书里查无此物**。被问「为什么用 httpx」答不出出处。且它和 `requests` API 高度重叠，属于净增依赖 |
| `urllib.request` | 标准库无依赖，但 Basic Auth 要手写 base64、JSON 要手动 load、没有 session 复用，代码量翻倍且更容易写错 |
| `pycurl` | 无必要，且错误信息难读 |

**实现要点（给 AI 的硬约束）：**

```python
# 同步：必须复用 session，不要每次 requests.get
_session = requests.Session()
_session.auth = HTTPBasicAuth("karaf", "karaf")
_session.headers["Accept"] = "application/json"

# 异步：aiohttp 的 session 必须由事件循环持有，不能每次 new
# Sanic 里挂在 app.ctx 上，用 app.add_task 管理生命周期
```

### 2.2 Web 框架：`Sanic` + `single_process=True`

**结论**：Sanic，单进程，端口 8000（对外给前端）。

**为什么 Sanic：** 实验⑦ 3.2 与 5.3.2 明确用它，且原生支持 WebSocket，不用额外装 `flask-sock` / `python-socketio`。

**为什么必须 `single_process=True`（这条是硬约束，不是优化）：**

大脑的全部状态——`graph`、`host_table`、`snapshot`、`deployed`（下发记录）——都放在**进程内存**里。
如果 Sanic 起 4 个 worker 进程：

- 轮询任务会被启动 4 次 → 4 份拓扑快照互相打架
- `deployed` 表在 A 进程写入，B 进程看不到 → 删除流表时会删错或删不掉
- WebSocket 连在 C 进程，拓扑变化发生在 A 进程 → 推不出去

→ **`app.run(host="0.0.0.0", port=8000, single_process=True, access_log=False)`**

**淘汰的替代品：**

| 候选 | 淘汰理由 |
|---|---|
| Flask | 实验书无出处；原生无 WebSocket，要装 `flask-sock` |
| FastAPI + uvicorn | 生态最好，但实验书无出处，且多一层 uvicorn 配置，要多解释一个组件 |
| 不用框架（`asyncio` + `websockets` 裸写） | 路由要手写，前端静态文件要手写 MIME，不值得 |

### 2.3 拓扑承载：Python `dict` 邻接表

**结论**：`dict[str, dict[str, dict]]`，有向存储，比对时用 `frozenset` 无向归一化。

```python
graph = {
    "of:0000000000000001": {
        "of:0000000000000002": {"sport": 1, "dport": 2, "weight": 1},
    }
}
```

**为什么不用 `networkx`：**

1. **实验书里没有**。被追问「这个库解决什么问题、为什么需要它」时，答案是「不需要，我们用字典就够了」——那就构成了选型失误。
2. `networkx.Graph` 内部本质也是 dict of dict。我们真正需要的功能只有：取邻居、算最短路。前者一行 `graph[u].items()`，后者手写 30 行 Dijkstra。
3. `networkx` 装不上/版本冲突时会拖死整个环境，而 `dict` 永远不会出问题。

**设计细节：**

- 存**有向**，因为每条边要记 `sport`（从 u 出发的端口）和 `dport`（对端端口），方向不同端口不同。
- **比对必须归一化**：`/links` 会把一条物理链路按两个方向各报一次，直接 `len(edges)` 会得到双倍。用 `frozenset({u, v})` 去重。

### 2.4 路径算法：手写 Dijkstra

**结论**：`heapq` + `dist` 字典，标准实现，额外返回每一跳的出端口。

**为什么手写：** 见 2.3 第 2 条。另外本题要在路径上「顺带带出端口信息」，库函数返回的只是一串节点，端口还得自己查——自己写反而更省事。

**为什么不用 Bellman-Ford / A\*：** 边权全为 1（或按链路容量），没有负权，A\* 没有可用的启发函数。选了反而要解释「你的启发函数怎么来的」。

**组播路径**：以源为根跑一次 Dijkstra 得到「单源最短路径树」（就是 `dist` 的 `parent` 指针构成的树），
再按需求集合剪枝得到组播树 → 每个节点上「朝下游方向的端口集合」即为 group 的 bucket 列表。

### 2.5 组播组表：`ovs-ofctl`（shell），不走 ONOS REST

**结论**：用 `sudo ovs-ofctl -O OpenFlow13 add-group <bridge> group_id=N,type=all,bucket=...` 下发。

**为什么不用 ONOS REST：** ONOS 2.7 的北向接口**没有 group 的 REST 端点**（只有 `/flows`、`/devices`、`/links`、`/hosts`、`/intents` 等）。
它靠 Intent 框架驱动 group，那是 ONOS 内部 Java 应用的活。我们的路线是纯 REST，所以组表只能落到 OVS 命令层面。

这是**已确认的架构缝隙**，必须主动说明：「组表通过 OVS 命令行直下，因为 ONOS 北向未暴露 group 资源；应用层仍在 ONOS 的流表域内」。不要说成「ONOS 支持组表下发」。

**风险**：`ovs-ofctl` 需要 sudo。抓取/下发都在 WSL 里、且 Python 以普通用户跑时，必须配免密 sudo
（`NOPASSWD`），代码里才能用 `subprocess.run(["sudo","ovs-ofctl",...])`；否则这道命令会挂在密码提示上。
这是环境前提，不是代码能绕开的。

### 2.6 南向：OpenFlow 1.3，由 ONOS 代管

大脑**不直接**跟交换机说 OpenFlow。数据路径是：

```
大脑 --HTTP/JSON--> ONOS 北向 --> ONOS 南向(OpenFlow 1.3) --> OVS
```

论证价值：这正是「控制平面与数据平面分离 + 北向接口可编程」的实证。Wireshark 抓 6653 端口能看到 ONOS 发出的 FlowMod，可以用来证明「我们的流表真的到了数据平面」（实验④）。

### 2.7 前端：原生 HTML + 手写 SVG + WebSocket

**结论**：单个 `static/index.html`，内嵌 CSS/JS，不引入任何框架和 CDN。

**为什么不用 ECharts / D3 / vis.js：**

1. 实验书无出处。
2. **CDN 在国内不稳定**——本项目已经因为网络问题在 Docker 拉镜像上栽过一次，不该在演示环节再赌一次网络。
3. 需求只是「画几个圆 + 几条线 + 状态颜色」。手写 SVG：一台交换机一个 `<circle>`，一条链路一个 `<line>`，坐标由后端算好下发或前端简单布局。总共不到 150 行。

**通信方式**：页面加载时 `GET /api/state` 拿全量，之后 `WebSocket /ws/topo` 只接收增量变化（`diff` 结果），前端自己更新 DOM。这样拓扑不变时零流量。

## 4. 明确不用的东西（附说明口径）

| 不用 | 理由（一句话，可直接背） |
|---|---|
| `httpx` | 功能与 requests 重叠，且实验书未提及，属于净增依赖 |
| `networkx` | 所需功能仅「取邻居 + 最短路」，字典 + 30 行 Dijkstra 即可，且能完整讲解实现 |
| `ECharts` | 可视化需求极简；CDN 在国内不可靠，演示环节不能赌网络 |
| Maven / `.oar` / `onos-app` | 本项目的应用平面在 ONOS **之外**（走北向 REST），不写 OSGi 应用 |
| ONOS `groups` REST | ONOS 2.7 北向未暴露 group 资源，改用 `ovs-ofctl` |
| `DELETE /flows/application/{appId}` | 所有通信对共用一个 appId，按 appId 批量删会误删别人的流表 |
| `fwd` 应用 | 它会抢先把 table-miss 流量转发掉，必须 `app deactivate org.onosproject.fwd` |

## 5. 技术风险与备选方案

| 风险 | 概率 | 影响 | 备选/缓解 |
|---|---|---|---|
| Sanic 25.12.1 在本机 Python 3.10 上起不来 | 低 | 阻塞应用层 | 降级到 `sanic==22.12`；再不行换 Flask + `flask-sock`，但需在文档里记录偏离实验书的原因 |
| `aiohttp` 与 Sanic 的事件循环冲突（session 生命周期） | 中 | WebSocket 卡顿 | 主链路退回 `requests` + `asyncio.to_thread`（Python 3.10 有），仍满足实验书要求 |
| `ovs-ofctl` 需要 sudo，进程内调用失败 | 中 | 组播做不了 | 提权脚本单独跑；或组播降级为「用流表手工复制」并在报告里说明局限 |
| 主机 `ipAddresses` 为空导致 `host_table` 建不起来 | 高（已知坑） | 路径算不出来 | 启动前强制 `pingall`；代码里对空 IP 打 WARNING 而不是静默跳过 |
| `/links` 双向重复导致算出的路径「来回跳」 | 高（已知坑） | 路径错误 | `frozenset` 归一化 + 建图时 `sport` 取实际方向 |
| ONOS 在演示时 `fwd` 没关干净 | 中 | 结果不可信 | 启动脚本里显式 `app deactivate` 后再 `app list` 核对 |
